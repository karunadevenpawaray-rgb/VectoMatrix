# VectoMatrix Features and User Types

The VectoMatrix Travel & Tours ecosystem is designed to accommodate multiple distinct user types, each with their own specialized workflows and permissions. The system is governed by a robust Row Level Security (RLS) implementation in Supabase when operating in live mode, and a centralized `mock-engine` when offline.

## User Types and Roles

### 1. Super Admin (The Creator)
The Super Admin is the system owner. They have ecosystem-wide access.
*   **Authentication**: Authenticated via Supabase Auth. Their UUID must exist in the `public.super_admins` table.
*   **Access Level**: RLS policies for all tables (`packages`, `agencies`, `leads`) have a bypass clause for users in the `super_admins` table.
*   **Features**:
    *   Can view, edit, and delete ALL packages and leads across ALL travel agencies.
    *   Access to the **Hidden Mock Admin Dashboard** (`/mock-admin`) to configure artificial network latency, simulate errors, and factory reset mock data across the ecosystem.

### 2. B2B Travel Agency
Agencies are the vendors utilizing the SaaS platform to sell their travel packages.
*   **Authentication**: Authenticated via Supabase Auth. Their UUID is linked to their respective `agency_id`.
*   **Access Level**: RLS restricts them to ONLY view and modify data (`packages` and `leads`) associated with their own `agency_id`.
*   **Features**:
    *   **Inventory Management**: Create, edit, and archive travel packages (destinations, base prices, hotel details).
    *   **Lead Management**: View incoming leads generated by the Web and Mobile apps. Update lead statuses (e.g., from `PENDING` to `CONVERTED`).
    *   **Automated Communications**: When a lead is marked as `CONVERTED`, the system automatically triggers an SMTP email containing the receipt and itinerary to the customer.

### 3. Consumer (B2C Web User)
The standard traveler interacting with the public-facing Web App.
*   **Authentication**: Typically unauthenticated or guest users. 
*   **Features**:
    *   **Discovery Feed**: Browse active packages across all agencies.
    *   **Search & Filter**: Filter packages by destination, month, hotel rating, and maximum price.
    *   **Secure Checkout**: Purchase packages using Stripe Integration. Payments securely capture funds and instantly create linked Leads in the database.

### 4. Mobile User (React Native App User)
Travelers using the iOS/Android mobile application.
*   **Authentication**: Managed locally via the app.
*   **Features**:
    *   **Offline-First Architecture**: The mobile app utilizes the shared `@vectormatrix/mock-engine` powered by `AsyncStorage`.
    *   **Offline Booking Queue**: If the user loses internet connection during checkout (or if a 500 network error is simulated), the booking payload is safely stored in a local device queue (`vmx_offline_queue`).
    *   **Customer Dashboard**: A digital itinerary wallet. It actively detects pending offline bookings and provides a "Sync Now" UI mechanism to batch-upload reservations once connectivity is restored.

## Core Ecosystem Features

### Centralized Mock Engine
A powerful developer and offline-first feature. The `@vectormatrix/mock-engine` is an NPM workspace library injected into Web, Admin, and Mobile. 
*   **True Persistence**: It relies on an abstracted Storage Adapter (`localStorage` for web, `AsyncStorage` for mobile) so data persists across browser reloads.
*   **Simulation**: Capable of simulating network delays (latency) and failure rates, making UI/UX testing for loading and error states incredibly easy.

### Stripe Financial Integration
The Web app integrates with Stripe for live payment processing. 
*   **Two-Step Verification**: Upon checkout, a `PENDING` lead is created in Supabase first. Its ID is embedded in the Stripe Session metadata.
*   **Webhook Fulfillment**: Once Stripe confirms the payment, webhooks securely update the Lead status to `PAID`.

### Automated SMTP Email Engine
Integrated within the `admin` ecosystem, the Next.js API handles automated emails. When agencies convert a lead, the system uses configurable SMTP credentials to dynamically inject user data into HTML email templates and dispatch booking confirmations.

## Business Rules & Ecosystem Engine Rules (Travel Lounge 2026 Integration)

Based on the expanded ecosystem integration, the system strictly adheres to the following business logic parameters:

### 1. Platform Security & Access Rules
* **Admin Verification & RBAC:** Write operations to inventories, pricing, and settings are governed by `is_admin_v2()`. Staff access requires an explicit linkage in the `public.admins` table.
* **Row-Level Security (RLS):** Guests are restricted to `SELECT` on catalog tables. Customers only have access to their own `profiles` and `bookings`.

### 2. Advanced Pricing Engine
* **Calculation Model:** Calculates lead prices dynamically on the database side (e.g., binding "As from" prices to Double Occupancy).
* **Mode Segregation:** Supports *Per Night* logic (for Hotels, additive by age) and *Per Person* logic (for Activities/Packages, multiplicative).
* **Occupancy Tiers:** Prices split into: Adult (18+), Teen (13-17), Child (2-12), and Infant (0-2).
* **Fallback Priority:** Grid Overrides > Base Rates > Zero-Rate Safety Guards.

### 3. Lodging & Meal Plan Rules
* **Meal Plans:** Bed & Breakfast (BB), Half Board (HB), Full Board (FB). All-Inclusive is strictly deprecated.
* **Self-Healing UI:** If an admin removes a meal plan, the booking wizard will dynamically self-heal to fallback to BB.

### 4. Service Fee & Markup Engine Rules
* **Percentage-Based Markup:** Customer-facing pricing is gross pricing driven by percentage markups over net vendor rates.
* **Hierarchy:** Row-Level Overrides > Room Type Override > Service Default Markup > 0%.

### 5. Inventory & Availability (Stop-Sell) Rules
* **Stop-Sell Priorities:** Any date flagged `is_stop_sell = true` is universally blocked for booking.
* **Discovery Evasion:** Search bars bypass stop-sell validation to reduce discovery friction, but checkout wizards rigidly enforce calendar blockages and force re-hydration on conflicts.

### 6. Booking & Transaction Rules
* **References:** Generates human-readable IDs (`TL-XXXXXX`).
* **Atomicity:** Ensures bookings, user profiles, and payments are handled securely in one transaction via `create_booking_v1`.

### 7. Notification & Email Communication Rules
* **Asset URL Normalization:** Before SMTP dispatch, system emails resolve relative DB asset URLs into absolute storage URLs to prevent layout collapse.
